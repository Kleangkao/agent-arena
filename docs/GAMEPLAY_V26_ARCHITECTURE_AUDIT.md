# AGENT ARENA V2.6 architecture audit

26 November 2026 · Decision for owner review

**Recommendation.** Keep the fixed-step TypeScript authority and the existing model-authored conditional executor. First measure executable activity, expose real movement and reload cues, and replace the fixed renewal trigger with coverage-aware checkpoints under the existing budget. Test one-slot asynchronous prefetch only if network wait still dominates preparation or the product moves to truly live simulation. Gameplay feel needs a fresh owner playtest. The single-site Objective Duel results confound map layout, roles and scripted policy and provide no basis for tuning Core timing, equipment or scoring.

## 1. Verified repository findings

### From protected request to displayed match

1. The protected API validates the guest and trial token, reserves application capacity, and locks participants, arena configuration and coaching revisions. For V2.6 it records zero memory revisions and passes coaching without memory to the runner. The prompt builder can include compatible memory, but V2.6 reflection and hosted reuse remain incomplete. [API reservation and runner](../server/api.ts#L110) · [Prompt](../src/v26/controller.ts#L116)
2. On each 30 Hz simulation boundary the runner observes both sides, checks existing plans, and applies request eligibility. When both sides request at the same boundary, the calls run concurrently from the same pre-step state. The shared simulation waits for the request batch, including retries, before it advances. The existing flow prepares a complete or interrupted recording. In this flow wall-clock provider latency delays preparation rather than advancing an unattended match. A request has an 8-second timeout, a match has a 60-second deadline, retries count toward 10 attempts per side and 20 total, and a 429 ends the trial without retry. [Runner](../server/gameplay-v26.ts#L7)
3. The executor evaluates typed stages, guards, completion, interruption and leases at simulation boundaries. It can switch to an already-authored alternative immediately. The input validator still checks the resulting packets. The engine applies compatible inputs, resolves movement and due actions, settles the mode, and produces filtered observations. Replay v6 reconstructs from the saved config and packet transcript and compares events, receipts and final state. It needs zero provider calls. [Executor](../src/v26/controller.ts#L62) · [Engine](../src/v26/game.ts#L163) · [Replay](../src/v26/replay.ts#L29)
4. **Start sandbox** runs the scripted Sand policy in the browser. It shares the plan executor and the engine with the protected runner. Its plan selection has no provider requests, retry delay or reserved scheduler. The benchmark uses injected provider responses, including artificial errors. Genuine V2.6 models were outside both paths. [Sandbox](../src/v26/sandbox.tsx#L83) · [Scripted policy](../src/v26/development.ts#L29) · [Injected cases](../scripts/evaluate-gameplay-v26.ts#L93)

### The 8.3 seconds came from the plan and scheduler

Replayed the saved Score Deathmatch retry scenario, seed 12, through the unmodified runner. The temporary read-only harness fed back the saved validated plans and injected 503s and asserted the original request tick for every attempt. Walking the resulting frames through the same executor recovered the exact gap.

| Blue boundary | What happened |
|---|---|
| Tick 300 · 10.00 s | The scheduled request saw an injected 503, retried successfully on the same tick and spent two attempts. |
| Tick 387 · 12.90 s | First living boundary after respawn. This priority request bypassed the rolling allowance and brought Blue to four attempts. |
| Tick 595 · 19.83 s | The three stages had finished after 208 ticks, or 6.93 seconds, although the plan's declared lifetime was 10 seconds. The initial empty alternative met `action-finished` on the next boundary in Score. The remaining stages were 5.5 and 1.4 seconds. The reserved cadence gives completion and expiration no immediate renewal trigger. |
| Tick 687 · 22.90 s | The ten-second scheduled interval became due and the plan lifetime expired. The allowance still gave four attempts, already spent. |
| Tick 844 · 28.13 s | The allowance reached five and a replacement was accepted. Gap **249 ticks = 8.30 s**, split into 92 completed-plan ticks and 157 expired-plan ticks. |

The retry contributed through budget accounting. The 8.30 seconds were simulated time with no valid plan, with the scheduler keeping that gap even on an immediate provider. Blue also had a 248-tick gap ending at the Score clock. Blue used nine of ten hard-cap attempts. Moving a request earlier after this respawn would require changing which allowance funds it, or extending the executable horizon with behavior the model actually authorizes. A 6.93-second horizon would require eleven successful plans to cover 75 seconds continuously, even before retries and guard failures.

In a read-only comparison, injecting 80 ms into each of the 18 attempts changed match preparation from **163 ms to 1,234 ms** on this machine. This is a test of clock coupling, with no estimate of Gemini latency. ### Coverage, feedback and staleness

- **Plan coverage includes guard waits.** The retry case had 63.33% coverage across 142.8 eligible agent-seconds, yet 77.37 agent-seconds had no accepted action, active motion flag or in-flight action by the existing metric. Of those, 51.60 seconds lacked a valid plan. Only 1.00 second was counted as an explicit empty-packet wait. A guard with no selectable branch, exhausted repeats, an owned action in progress, and an explicit wait need separate reporting. An accepted facing or stop packet can count as activity with zero displacement. Position delta and combat or Core progress are separate measures. [Timing implementation](../server/gameplay-v26.ts#L109) · [Per-side measurements](../evidence/gameplay-v26-playtest/benchmark.json)
- The injected Score retry case produced 217 authorized feedback records, delivered 174 on successful requests, had 30 pending at the end, and dropped 13 by overflow. The current queue holds 16 records per side. Repeated receipts or collision events can consume that capacity. The aggregate shows overflow, with no proof of which strategically important events were lost. The retry reuses the same prompt snapshot at the paused boundary. [Feedback filter](../src/v26/controller.ts#L102) · [Queue and request handling](../server/gameplay-v26.ts#L59)
- Within one attempt the simulation stays frozen, and the timeout race prevents a late resolution from overwriting an accepted plan. Explicit request sequence, source tick, life, phase, feedback cursor and expiry checks become necessary if the simulation can advance while requests are in flight. Current contact and legal capability changes matter even inside a plausible age limit. The no-overlap path today also immediately interrupts when its request chain fails, even if an older plan might still have useful authorized work. Hard-budget exhaustion currently drains eligible underway actions before interrupting. [Request and failure paths](../server/gameplay-v26.ts#L22)

### Why the scripted opponent can still feel unnatural

The focused tests showed that different inputs and results are possible. Normal play has repeating transitions through contact, movement, reload, collision and objective states. The scripted policy usually reauthors on a nominal 450 ms interval, with an earlier refresh when standard attack becomes legal. During reload it can steer directly away at less than or equal to 1.5 tiles, go toward a role-qualified Core goal, or stop. Those decisions can switch abruptly at the distance threshold. Otherwise a fallback goal can use an observed or last-seen position, including a position that invites collision during pursuit. These are concrete paths that could explain the report. The owner's latest exact input sequence and event trace were unavailable, so the dominant cause in that session is uncertain. [Development policy](../src/v26/development.ts#L7) · [Focused tests](../test/gameplay-v26-playtest.test.ts)

The canvas draws the latest committed positions, crouch and airborne silhouettes, facing, and flashes from resolved attack events. It does not show active reload, firing wind-up, blocked steering, or a move gait cycle. The HUD shows ammo, and the debug observation exposes timers. Under catch-up, the interval publishes the latest position while the renderer consumes multiple stored events in one frame. The saved stall test proves event delivery and outcome, while accumulated cues can still be hard to distinguish and intermediate poses may never appear. A reload pause can therefore look like an idle bot, and a sharp direction change can be an actual policy choice or a display jump. Inspect both tracks in a normal session. ## 2. Research and architectural choices

- **Finite state machines** fit bounded lifecycle states such as ready, requesting, buffered, stale, interrupted, and existing engine states such as reloading. A single flat state machine would multiply independent movement and action combinations unnecessarily. Orkin's shipped example separates a small execution FSM from its planning layer. [Jeff Orkin, Three States and a Plan](https://www.gamedevs.org/uploads/three-states-plan-ai-of-fear.pdf)
- **Behavior trees** offer guarded sequences, selectors and aborts. Epic's event-driven implementation documents an observer waking an authored branch when a fact changes. V2.6 already evaluates equivalent small-scale guards each tick. Adopt clear reasons for branch changes and bounded wake-ups. A tree framework, editor or second execution engine has little value for four bounded stages. [Epic Behavior Tree overview](https://dev.epicgames.com/documentation/unreal-engine/behavior-tree-in-unreal-engine---overview)
- **Utility AI** scores options on changing factors. It is a useful practice-policy candidate for smooth distance preferences or testing hysteresis. In genuine competition the scoring layer could choose strategy behind the model's back. If introduced there later, the model would need explicit ownership of the allowed options and preference bounds. [David Graham, An Introduction to Utility Theory](https://www.gameaipro.com/GameAIPro/GameAIPro_Chapter09_An_Introduction_to_Utility_Theory.pdf)
- **GOAP and HTN** solve different planning problems. GOAP searches action preconditions and effects to satisfy a goal. HTN decomposes compound tasks into domain-authored methods. Both shipped in larger domains, with additional search or domain-authoring costs. V2.6 can use explicit conditions and named, validated intents without symbolic world duplication, recursive decomposition or a planner that makes strategic choices for the model. [Orkin's shipped GOAP design](https://www.gamedevs.org/uploads/three-states-plan-ai-of-fear.pdf) · [Guerrilla's shipped HTN design](https://www.guerrilla-games.com/read/killzone-2-multiplayer-bots)
- **Hierarchical LLM execution** fits the existing split. The model chooses goals, preferences and contingencies from filtered observations, coaching and compatible memory. The deterministic executor grounds those choices in legal capabilities. SayCan demonstrates the principle in a different domain. V2.6 should use only validated data and the existing authoritative input validator. [Ahn et al., SayCan](https://arxiv.org/abs/2204.01691)
- **Asynchronous planning and buffering** can overlap execution with inference while increasing observation age. Black et al. demonstrate overlap and continuity at chunk boundaries in robotics. Sendai et al. show why long chunks and aging observations weaken reactivity. These support testing overlap and stale-response rejection as design hypotheses. Their task-specific results provide no expected performance figure for AGENT ARENA. [Black et al., Real-Time Execution of Action Chunking Flow Policies](https://www.pi.website/download/real_time_chunking.pdf) · [Sendai et al., Leave No Observation Behind](https://arxiv.org/abs/2509.23224)

| Alternative | Latency and cost | Complexity, fairness and replay | Autonomy, continuity and failure |
|---|---|---|---|
| **A. Coverage-aware synchronous checkpoints** | Targets simulated gaps directly. Retains current per-request wall-time barrier. Same hard caps, with attempts shifted from periodic to earlier useful checkpoints. Compact observations can limit token growth. | Low. Both sides can receive the same tick cut-off and budget rules. Replay format remains packet-based. | Model still authors preferences and contingencies, with locked coaching and compatible memory. On failure finish only still-legitimate authored work within limits, then record interruption. |
| **B. One in-flight and one buffered plan per side** | Overlap can hide part of network wait against executable work. Current faster-than-real-time preparation offers little wall-clock overlap from simply advancing ticks. Discarded responses and retry still cost calls and tokens. Replace a planned request with a prefetch. | Medium. Use a deterministic commit boundary or a symmetric bounded pause. Receipt order alone would let provider latency affect competition. Record apply ticks and dispositions, and verify packet replay. | Preserve strategy during handoff. Buffer an early validated candidate. Activate only if it remains fresh, version-bound and applicable. Continue the valid current plan and interrupt on exhausted continuity. |
| **C. One fuller authored conditional policy with sparse event checkpoints** | Fewer round trips. More tokens per response and possibly longer first call. Conditional branches could increase coverage without a new request, with an increased stale-policy risk. | Medium. Requires stronger bounds, branch validation and comprehensible trace. Both sides receive the same policy capabilities and horizon. Same packet replay. | Model retains authorship but has fewer chances to use fresh observations or feedback. Pin coaching and compatible memory. Use only legal authored branches on outage. |
| **D. Scripted FSM or utility for practice** | No API or token cost. Tick-bound response. | Low for a compact policy and testable choice reasons. Replay already works. Evaluate in labeled practice cohorts. | Can improve practice feel and expose engine problems. Genuine coaching/memory and provider-failure evidence require the model path. |
| **E. Full behavior tree framework, GOAP or HTN planner** | Local evaluation may be fast. It cannot hide provider latency by itself. Adding model goals retains provider calls and can add context burden. | High for this scope. Requires deterministic order, tie-breaks, domain modeling and a second strategy layer. | Autonomous local planning would shift meaningful decisions away from the model. Suitable for later complex authored practice if justified. |

Input savings and latency should be measured separately. Start by separating stable public schema/map context from compact per-side dynamic observations and deduplicating routine feedback. Provider caching can reduce repeated-prefix cost on supported configurations. It does not resolve lack of an executable plan or establish savings for this model and account. [Gemini API context caching](https://ai.google.dev/gemini-api/docs/caching)

## 3. Priorities and validation proposal

**P0 · Observe before tuning.** Capture instrumented, ordinary sandbox sessions with a small recent ring of match tick, authoritative speed, reload due time, contact, plan/branch reason, request reason where applicable, inputs and receipts. Capture synchronized video with the overlay hidden during the actual playtest. Show a minimal reload cue and distinguish movement progress from blocked intent using existing authoritative state and events. Label planned wait, guard wait, held action, incompatible input, blocked movement and missing plan separately. Inspect sequences of reload while moving, stopped reload, objective approach, collision, direction changes, and recovery from lost contact. Preserve map, Core, equipment and scores.

**P0 · Compare the existing scheduler with A.** Use the exact Score retry and short-horizon traces plus Objective phase-change, clustered respawn, budget exhaustion and explicit-wait fixtures. Base renewal on the earliest likely loss of executable coverage, purposeful phase/life changes and execution failure, with hysteresis and budget accounting. Keep 10/side, 20 total, existing timeouts and retry limits. Test reallocation within the existing budget, including the effect of a priority call bypassing the allowance. Compare a slightly longer *model-authorized* contingency horizon if shorter plans cannot cover the clock under those caps. A timer extension alone is insufficient. Persist interruption reason and partial recording, with no competitive result, settlement or ordinary reflection credit.

**P1 · Test B only when measurements justify it.** Bound lookahead to one request and one validated candidate per side. Bind candidate to match, side, sequence, source tick, life, relevant phase, rules/map, coaching and memory revisions. Test maximum observation age and current prerequisites at activation. Revalidate via the same engine before commit. Coalesce triggers while in flight. Carry feedback cursors so accepting a request cannot wipe events that arrived afterward, and prioritize contact/phase/life transitions over routine receipt noise. Use a defined activation boundary, symmetrical deadline and reproducible policy for late, cancelled and out-of-order responses. For prepared play, compare same-tick barriers with a deterministic future commit tick. For a later live mode, quantify whether equal budgets still yield unequal advantages under asymmetric provider latency.

**Test matrix and proposed gates.**

- Run fixed seeds for both roles and sides with distributions explicitly labeled synthetic. Start with zero-latency, a 100–300 ms band, a 0.5–2 second band and a long tail of 4–8 seconds, plus forced timeouts, one 503 then recovery, 429, illegal or malformed plans, cancellation, duplicate and late responses, and asymmetric delays. Include guard condition inversion, reload compatibility, clustered respawns, Core phase transition and base-clock end. Report seed, attempt schedule, simulated and wall-clock units separately.
- Report p50/p95/p99 and max for request time, observation age on activation and gap duration. Report time to first playable replay, total preparation, retry time, attempted/completed/rejected/wasted requests, prompt and output tokens where measured, valid plan coverage, time with authorized executable behavior, measured displacement or progress, and longest infrastructure-idle gap. Separate explicit authorized waits, guard waits, legal but stationary commitments, blocked moves, time after technical interruption, and actual uncovered living time. Example review targets are p95 infrastructure-idle gaps under 1 simulated second and no gap over 2 seconds in nominal synthetic trials. Outage trials should terminate cleanly under the agreed deadline when continuity cannot be maintained. These proposed thresholds and the existing 30–60 second preparation target require measurement and owner review.
- Check symmetry through deterministic role/side swaps and swapped latency schedules, and quantify accept/discard rates and reasons. Reconstruct every completed and partial replay without provider calls. Compare config, packet sequence, apply ticks, receipts, ordered events and result. Confirm stale plans never cross respawn, phase invalidation, match completion or version boundaries. V1 Testnet proof applies to V1. The V2.6 check here concerns local replay integrity.
- Measure browser frame times and catch-up on desktop and a slower viewport/device. Use normal playback, a controlled stall, and assertions comparing displayed reload/motion states with authoritative ticks. Record visual readability of repeated cues and input-to-presentation delay. End with the owner playing both modes through ordinary sequences and reviewing synchronized clips. Automated correctness remains a separate gate from gameplay feel.
- After owner review and explicit trial authorization, use one protected Objective Duel and a role swap if capacity permits. Verify meaningful model-authored choices before drawing coaching conclusions. Freeze coaching and compatible memory at reservation. Later verify persistence and actual reuse across genuine completed matches. Retain existing application and provider controls.
